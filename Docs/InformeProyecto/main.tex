\section{Justificación de la arquitectura de microservicios}

El sistema se divide en dos servicios .NET 8 independientes que se comunican
por HTTP, sin API Gateway ni contenedores. Cada uno cumple las cuatro
características que definen un microservicio, con evidencia concreta en el
código del repositorio.

\subsection{Business Function}

\textbf{Definición}: cada microservicio resuelve una única responsabilidad de
negocio, no un conjunto de funciones técnicas mezcladas.

En este proyecto la división es explícita: \texttt{AuthService} se ocupa
únicamente de la autenticación (login y firma de JWT), y
\texttt{AssetsService} de la gestión y el cálculo de activos. Cada servicio
expone su propio controlador con rutas REST dedicadas:

\begin{lstlisting}[style=csharp, caption={AuthService.Api/Controllers/AuthController.cs (fragmento)}]
[ApiController]
[Route("api/auth")]
public class AuthController : ControllerBase
{
    [HttpPost("login")]
    public async Task<IActionResult> Login([FromBody] LoginRequest request)
    {
        var response = await _login.EjecutarAsync(request);
        ...
    }
}
\end{lstlisting}

\begin{lstlisting}[style=csharp, caption={AssetsService.Api/Controllers/ActivosController.cs (fragmento)}]
[Authorize]
[ApiController]
[Route("api/activos")]
public class ActivosController : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Crear([FromBody] ActivoRequest request) ...

    [HttpGet("{id}/depreciacion")]
    public async Task<IActionResult> Depreciacion(int id) ...
}
\end{lstlisting}

\textbf{Por qué aplica}: \texttt{AuthController} solo conoce credenciales y
tokens; \texttt{ActivosController} solo conoce activos y depreciación. Ningún
controlador mezcla ambas responsabilidades, y cada servicio puede evolucionar
su lógica sin afectar al otro.

\subsection{API Communication}

\textbf{Definición}: los microservicios se comunican exclusivamente por API
REST sobre HTTP; no comparten memoria, objetos ni proceso.

Ambos servicios exponen endpoints REST y el frontend los consume por HTTP. El
archivo \texttt{frontend/src/api.js} define las dos URLs base y usa
\texttt{fetch} para cada llamada:

\begin{lstlisting}[style=json, caption={frontend/src/api.js (fragmento)}]
const AUTH_URL = 'http://localhost:5001'
const ASSETS_URL = 'http://localhost:5002'

export async function login(username, password) {
  return request(`${AUTH_URL}/api/auth/login`, { ... })
}

export async function listarActivos() {
  return request(`${ASSETS_URL}/api/activos`, { headers: authHeaders() })
}
\end{lstlisting}

\textbf{Por qué aplica}: cada petición viaja como JSON sobre HTTP y el
servidor responde con JSON; no hay llamadas directas entre procesos ni
variables compartidas entre servicios.

\subsection{Independent Operation}

\textbf{Definición}: cada microservicio corre como un proceso independiente,
con su propio puerto, su propia configuración y su propia base de datos; se
puede detener uno sin tumbar al otro.

Cada servicio se levanta con su propio \texttt{dotnet run} en un puerto
distinto (\texttt{launchSettings.json}) y apunta a su propia base de datos
(\texttt{appsettings.json}):

\begin{lstlisting}[style=json, caption={AuthService.Api/Properties/launchSettings.json (fragmento)}]
"profiles": {
    "http": {
      "applicationUrl": "http://localhost:5001",
      ...
    }
}
\end{lstlisting}

\begin{lstlisting}[style=json, caption={AssetsService.Api/Properties/launchSettings.json (fragmento)}]
"profiles": {
    "http": {
      "applicationUrl": "http://localhost:5002",
      ...
    }
}
\end{lstlisting}

\begin{lstlisting}[style=json, caption={appsettings.json de cada servicio (fragmentos)}]
// AuthService.Api/appsettings.json
"ConnectionStrings": {
    "AuthDB": "Server=localhost;Database=AuthDB;User Id=auth_user;..."
}

// AssetsService.Api/appsettings.json
"ConnectionStrings": {
    "AssetsDB": "Server=localhost;Database=AssetsDB;User Id=assets_user;..."
}
\end{lstlisting}

\textbf{Por qué aplica}: cada servicio tiene su propio puerto (5001 y 5002) y
su propia base de datos (AuthDB y AssetsDB) con usuarios de SQL Server
distintos (\texttt{auth\_user} y \texttt{assets\_user}); detener
\texttt{AuthService} no impide que \texttt{AssetsService} siga respondiendo.

\subsection{Request Handling}

\textbf{Definición}: el enrutamiento de cada petición hacia el microservicio
correcto es una decisión explícita; en este caso la toma el cliente (no hay
API Gateway).

El frontend decide a qué servicio llamar según la operación, en
\texttt{frontend/src/api.js}: login siempre va a \texttt{AUTH\_URL} (5001) y
las operaciones de activos/depreciación a \texttt{ASSETS\_URL} (5002):

\begin{lstlisting}[style=json, caption={frontend/src/api.js (fragmento)}]
// ---------- AuthService (puerto 5001) ----------
export async function login(username, password) {
  return request(`${AUTH_URL}/api/auth/login`, { ... })
}

// ---------- AssetsService (puerto 5002) ----------
export async function obtenerDepreciacion(id) {
  return request(`${ASSETS_URL}/api/activos/${id}/depreciacion`, { ... })
}
\end{lstlisting}

\textbf{Por qué aplica}: no existe un gateway central; el enrutamiento es
explícito en el código del cliente, lo que simplifica la infraestructura
(acorde con la decisión de no usar contenedores) manteniendo el desacople
entre servicios.

\section{Justificación de Onion Architecture}

\textbf{Por qué Onion y no una arquitectura en capas simple}: en una
arquitectura en capas tradicional (Controllers $\rightarrow$ Services
$\rightarrow$ Repositories $\rightarrow$ DbContext), la capa de persistencia
es la más interna y todo depende de ella: si se cambia el motor de base de
datos, se reescribe el resto. Onion Architecture invierte esa dependencia: el
\textbf{Domain} (reglas de negocio) queda en el centro sin depender de nada,
y la persistencia pasa a la periferia, dependiendo de las interfaces que el
centro define.

La regla de dependencia se cumple a nivel de compilador porque cada capa es
un proyecto .NET separado:

\begin{itemize}
    \item \texttt{Domain} no referencia a nadie.
    \item \texttt{Application} referencia solo a \texttt{Domain}.
    \item \texttt{Infrastructure} referencia a \texttt{Application} y \texttt{Domain}.
    \item \texttt{Api} referencia a los tres (es quien hace el cableado final).
\end{itemize}

La verificación con \texttt{dotnet list reference} confirma la regla en el
proyecto más interno:

\begin{lstlisting}[style=json, caption={Verificación de la regla de dependencia}]
$ dotnet list AssetsService.Domain/AssetsService.Domain.csproj reference
There are no Project to Project references in project
AssetsService.Domain/AssetsService.Domain.csproj.
\end{lstlisting}

El archivo \texttt{AssetsService.Domain.csproj} lo confirma: no contiene
ningún \texttt{ProjectReference} ni paquete de persistencia:

\begin{lstlisting}[style=json, caption={AssetsService.Domain/AssetsService.Domain.csproj}]
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
\end{lstlisting}

El beneficio concreto: \texttt{Domain} y \texttt{Application} nunca importan
\texttt{Microsoft.EntityFrameworkCore}; la persistencia es un detalle
intercambiable que vive en \texttt{Infrastructure}.

\section{Contraste de conceptos de Clean/Onion Architecture contra el código real}

\subsection{Entidades de dominio}

\textbf{Definición}: las entidades son los objetos de negocio puros del núcleo
de la aplicación: contienen datos y comportamiento de negocio, y no dependen
de ninguna infraestructura (ni base de datos, ni HTTP, ni frameworks).

En el proyecto, \texttt{Activo} vive en \texttt{AssetsService.Domain/Entities}
y solo usa anotaciones del BCL de .NET (\texttt{System.ComponentModel.DataAnnotations}),
nunca \texttt{EntityFrameworkCore}:

\begin{lstlisting}[style=csharp, caption={AssetsService.Domain/Entities/Activo.cs}]
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

namespace AssetsService.Domain.Entities;

[Table("Activos")]
public class Activo
{
    [Key]
    public int Id { get; set; }

    [Column("categoria_id")]
    public int CategoriaId { get; set; }

    [Column("nombre")]
    public string Nombre { get; set; } = string.Empty;

    [Column("precio_compra")]
    public decimal PrecioCompra { get; set; }

    [Column("fecha_compra")]
    public DateTime FechaCompra { get; set; }

    [Column("fecha_corte")]
    public DateTime FechaCorte { get; set; }

    [Column("fecha_registro")]
    public DateTime FechaRegistro { get; set; }

    [ForeignKey("CategoriaId")]
    public Categoria? Categoria { get; set; }
}
\end{lstlisting}

\textbf{Por qué aplica}: la entidad se limita a modelar el activo con sus
atributos y su relación con \texttt{Categoria}; al no importar EF Core, puede
persistirse con cualquier motor sin modificar esta clase.

\subsection{Reglas de negocio en el dominio}

\textbf{Definición}: las reglas de negocio son el conocimiento del dominio que
no depende de la tecnología; en Onion viven en el centro (Domain), aisladas de
la base de datos y del HTTP.

\texttt{DepreciacionService} contiene la fórmula oficial de depreciación
(años completos + resto parcial en meses) sin ninguna referencia a
persistencia ni a controladores:

\begin{lstlisting}[style=csharp, caption={AssetsService.Domain/Services/DepreciacionService.cs (fragmento)}]
public class DepreciacionService
{
    public List<FilaDepreciacion> CalcularTabla(Activo activo, Categoria categoria)
    {
        // VD = VALOR_COMPRA - VALOR_COMPRA * 0.10
        decimal valorDepreciable = activo.PrecioCompra - activo.PrecioCompra * 0.10m;

        // VDA = VD / VIDA_UTIL_ANIOS ; VDM = VDA / 12
        decimal vda = valorDepreciable / categoria.VidaUtilAnios;
        decimal vdm = vda / 12;

        DateTime finVidaUtil = activo.FechaCompra.AddYears(categoria.VidaUtilAnios);
        DateTime limite = activo.FechaCorte < finVidaUtil ? activo.FechaCorte : finVidaUtil;
        ...
    }
}
\end{lstlisting}

\textbf{Por qué aplica}: el método recibe entidades (\texttt{Activo},
\texttt{Categoria}) y devuelve \texttt{FilaDepreciacion}; no sabe de dónde
vienen los datos ni quién consume el resultado, por lo que la regla de negocio
es probable de forma aislada (como en \texttt{DepreciacionApp.Tests}).

\subsection{Casos de uso (capa de Aplicación)}

\textbf{Definición}: los casos de uso orquestan la aplicación: reciben la
petición, llaman a las reglas de negocio del Domain y a los puertos
(interfaces), y devuelven el resultado; no contienen lógica de negocio propia.

\texttt{CalcularDepreciacionUseCase} obtiene el activo con su categoría a
través del puerto \texttt{IActivoRepository} y delega el cálculo en el
\texttt{DepreciacionService} del Domain:

\begin{lstlisting}[style=csharp, caption={AssetsService.Application/UseCases/CalcularDepreciacionUseCase.cs}]
public class CalcularDepreciacionUseCase
{
    private readonly IActivoRepository _activos;
    private readonly DepreciacionService _depreciacion;

    public CalcularDepreciacionUseCase(IActivoRepository activos, DepreciacionService depreciacion)
    {
        _activos = activos;
        _depreciacion = depreciacion;
    }

    public async Task<TablaDepreciacionResponse?> EjecutarAsync(int id)
    {
        var activo = await _activos.ObtenerConCategoriaAsync(id);
        if (activo == null || activo.Categoria == null) return null;

        var filas = _depreciacion.CalcularTabla(activo, activo.Categoria);

        return new TablaDepreciacionResponse
        {
            ActivoId = activo.Id,
            Nombre = activo.Nombre,
            Categoria = activo.Categoria.Nombre,
            PrecioCompra = activo.PrecioCompra,
            FechaCompra = activo.FechaCompra,
            FechaCorte = activo.FechaCorte,
            Filas = filas
        };
    }
}
\end{lstlisting}

\textbf{Por qué aplica}: el caso de uso no sabe cómo se persiste el activo
(eso lo decide Infrastructure) ni cómo se calcula la depreciación (eso lo
decide Domain); solo coordina ambos.

\subsection{Inversión de dependencias}

\textbf{Definición}: la dependencia apunta hacia las abstracciones, no hacia
los detalles: Application define la interfaz (el ``qué'') e Infrastructure la
implementa (el ``cómo''), de modo que el centro nunca conoce la
infraestructura.

La interfaz \texttt{IActivoRepository} vive en Application:

\begin{lstlisting}[style=csharp, caption={AssetsService.Application/Interfaces/IActivoRepository.cs}]
public interface IActivoRepository
{
    Task<Activo?> ObtenerConCategoriaAsync(int id);
    Task<List<Activo>> ListarAsync();
    Task<Activo> CrearAsync(Activo activo);
}
\end{lstlisting}

Y su implementación concreta con EF Core vive en Infrastructure:

\begin{lstlisting}[style=csharp, caption={AssetsService.Infrastructure/Persistence/ActivoRepository.cs}]
public class ActivoRepository : IActivoRepository
{
    private readonly AssetsDbContext _db;

    public ActivoRepository(AssetsDbContext db)
    {
        _db = db;
    }

    public async Task<Activo?> ObtenerConCategoriaAsync(int id)
        => await _db.Activos
            .Include(a => a.Categoria)
            .FirstOrDefaultAsync(a => a.Id == id);
    ...
}
\end{lstlisting}

\textbf{Por qué aplica}: Application dice ``necesito obtener un activo con su
categoría'' y Infrastructure responde ``lo resuelvo con EF Core''; por eso
Application no importa \texttt{Microsoft.EntityFrameworkCore} y el motor de
persistencia es intercambiable.

\subsection{DTOs como contrato de frontera}

\textbf{Definición}: los DTOs son los objetos que cruzan la frontera de la
aplicación (entrada/salida de la API); desacoplan el contrato JSON que ve el
cliente de las entidades internas del dominio.

\texttt{ActivoRequest} define exactamente lo que el cliente debe enviar al
crear un activo, sin exponer campos internos como \texttt{Id} o
\texttt{FechaRegistro}:

\begin{lstlisting}[style=csharp, caption={AssetsService.Application/DTOs/ActivoRequest.cs}]
namespace AssetsService.Application.DTOs;

public class ActivoRequest
{
    public int CategoriaId { get; set; }
    public string Nombre { get; set; } = string.Empty;
    public decimal PrecioCompra { get; set; }
    public DateTime FechaCompra { get; set; }
    public DateTime FechaCorte { get; set; }
}
\end{lstlisting}

\textbf{Por qué aplica}: el cliente envía y recibe DTOs (JSON), nunca la
entidad \texttt{Activo} directamente; si el modelo interno cambia, el contrato
de la API puede mantenerse estable.

\subsection{Inyección de dependencias}

\textbf{Definición}: el cableado final de las dependencias se hace en un único
punto de composición (el \texttt{Program.cs} de la capa Api), registrando cada
interfaz con su implementación concreta; los constructores solo reciben
abstracciones.

\begin{lstlisting}[style=csharp, caption={AssetsService.Api/Program.cs (fragmento)}]
// Inversion de dependencias: Application define el puerto (interfaz),
// Infrastructure la implementacion concreta. Api hace el registro.
builder.Services.AddScoped<IActivoRepository, ActivoRepository>();
builder.Services.AddScoped<ICategoriaRepository, CategoriaRepository>();

// Regla de negocio pura (Domain).
builder.Services.AddScoped<DepreciacionService>();

// Casos de uso (Application): orquestan Domain + puertos.
builder.Services.AddScoped<CrearActivoUseCase>();
builder.Services.AddScoped<CalcularDepreciacionUseCase>();
\end{lstlisting}

\textbf{Por qué aplica}: los controladores reciben \texttt{CalcularDepreciacionUseCase}
por constructor sin saber qué repositorio concreto hay detrás; cambiar
\texttt{ActivoRepository} por otra implementación solo requiere tocar esta
línea de registro.

\section{Modelo de datos}

\textbf{Database-per-service}: en una arquitectura de microservicios, cada
servicio es dueño de sus propios datos; no comparte esquema ni tablas con
otros servicios. Esto permite que cada base evolucione de forma independiente
y que un servicio nunca dependa del esquema interno de otro.

En este proyecto hay dos bases SQL Server separadas, creadas por el script
\texttt{scripts/modelo-datos.sql} (idempotente):

\begin{itemize}
    \item \textbf{AuthDB} (solo AuthService): tabla \texttt{Usuarios} con el
    hash BCrypt de la contraseña.
    \item \textbf{AssetsDB} (solo AssetsService): master-detail
    \texttt{Categorias} $\rightarrow$ \texttt{Activos}.
\end{itemize}

La relación maestro-detalle se define con una clave foránea con
\texttt{NO ACTION} (RESTRICT): no se puede borrar una categoría que tenga
activos. La vida útil vive en \texttt{Categorias}, no en el activo, para que
un cambio de regla recalcule todos los activos existentes:

\begin{lstlisting}[style=json, caption={scripts/modelo-datos.sql (fragmento)}]
CREATE TABLE dbo.Categorias (
    id              INT IDENTITY(1,1) PRIMARY KEY,
    nombre          NVARCHAR(50) NOT NULL UNIQUE,
    vida_util_anios INT          NOT NULL
);

CREATE TABLE dbo.Activos (
    id             INT IDENTITY(1,1) PRIMARY KEY,
    categoria_id   INT           NOT NULL,
    nombre         NVARCHAR(100) NOT NULL,
    precio_compra  DECIMAL(10,2) NOT NULL,
    fecha_compra   DATE          NOT NULL,
    fecha_corte    DATE          NOT NULL,
    fecha_registro DATETIME2     NOT NULL DEFAULT GETDATE(),
    CONSTRAINT FK_Activos_Categorias FOREIGN KEY (categoria_id)
        REFERENCES dbo.Categorias(id)
);
\end{lstlisting}

El principio de menor privilegio refuerza la separación: cada servicio se
conecta con su propio login de SQL Server con acceso solo a su base, nunca
con \texttt{sa}:

\begin{lstlisting}[style=json, caption={scripts/modelo-datos.sql (fragmento)}]
-- Login de AuthService
CREATE LOGIN auth_user WITH PASSWORD = 'AuthUser123!';
USE AuthDB;
CREATE USER auth_user FOR LOGIN auth_user;
ALTER ROLE db_datareader ADD MEMBER auth_user;
ALTER ROLE db_datawriter ADD MEMBER auth_user;

-- Login de AssetsService
CREATE LOGIN assets_user WITH PASSWORD = 'AssetsUser123!';
USE AssetsDB;
CREATE USER assets_user FOR LOGIN assets_user;
ALTER ROLE db_datareader ADD MEMBER assets_user;
ALTER ROLE db_datawriter ADD MEMBER assets_user;
\end{lstlisting}

\textbf{Por qué aplica}: \texttt{auth\_user} solo puede leer/escribir en
AuthDB y \texttt{assets\_user} solo en AssetsDB; si un servicio fuera
comprometido, el atacante no tendría acceso a los datos del otro servicio.

\section{Flujos principales}

\subsection{Autenticación}

El flujo de login recorre el frontend, el \texttt{LoginUseCase} de
Application y los puertos de Infrastructure:

\begin{enumerate}
    \item El usuario ingresa usuario y contraseña en React; \texttt{api.js}
    hace \texttt{POST /api/auth/login} hacia AuthService (puerto 5001).
    \item \texttt{AuthController} delega en \texttt{LoginUseCase.EjecutarAsync}.
    \item El caso de uso busca el usuario por nombre vía
    \texttt{IUsuarioRepository.ObtenerPorUsernameAsync} (EF Core consulta
    AuthDB).
    \item Si el usuario no existe, o \texttt{BCrypt.Verify} no coincide con el
    hash guardado, el caso de uso devuelve \texttt{null} y el controlador
    responde \texttt{401} con el mismo mensaje (no revela si el usuario
    existe).
    \item Con credenciales válidas, \texttt{IJwtService.GenerarToken} firma el
    JWT (HS256) y el controlador responde \texttt{200} con el token.
    \item React guarda el token en \texttt{localStorage} y lo reutiliza en el
    header \texttt{Authorization: Bearer} para las llamadas a AssetsService.
\end{enumerate}

\subsection{Creación y consulta de depreciación}

El flujo de activos tiene dos partes: primero se crea el activo y luego se
consulta su tabla de depreciación. Ambas requieren un JWT válido, que el
middleware de AssetsService valida antes de ejecutar el controlador:

\begin{enumerate}
    \item \textbf{Creación}: React hace \texttt{POST /api/activos} con el
    token; \texttt{CrearActivoUseCase} valida que la categoría exista
    (\texttt{ICategoriaRepository}) y persiste el activo
    (\texttt{IActivoRepository}); responde \texttt{201} con el activo creado,
    o \texttt{400} si la categoría no existe.
    \item \textbf{Consulta}: React hace \texttt{GET /api/activos/\{id\}/depreciacion};
    \texttt{CalcularDepreciacionUseCase} obtiene el activo con su categoría
    (\texttt{IActivoRepository.ObtenerConCategoriaAsync}) y delega el cálculo
    en \texttt{DepreciacionService.CalcularTabla} (regla de negocio pura del
    Domain).
    \item El caso de uso arma la \texttt{TablaDepreciacionResponse} con las
    filas anuales y el controlador responde \texttt{200}.
\end{enumerate}

\section{Corrección de la lógica de depreciación}

\textbf{El problema}: la primera versión de \texttt{DepreciacionService}
generaba una tabla \textbf{mensual} (una fila por mes, sumando VDM en cada
una). AGENTS.md exige una tabla \textbf{anual}: una fila por año completo con
VDA, y si la fecha de corte no coincide con un aniversario exacto de la
compra, una última fila \textbf{parcial} calculada en meses completos usando
VDM solo para ese resto.

\textbf{El algoritmo corregido} (AGENTS.md, sección ``Fórmula de
depreciación (corregida)''):

\begin{enumerate}
    \item \texttt{VD = VALOR\_COMPRA - VALOR\_COMPRA $\times$ 0.10} (el activo
    termina su vida útil en el 10\% de su valor de compra).
    \item \texttt{VDA = VD / VIDA\_UTIL\_ANIOS} (depreciación por año
    completo) y \texttt{VDM = VDA / 12} (depreciación por mes, solo para la
    fila parcial final).
    \item \texttt{finVidaUtil = fechaCompra.AddYears(vidaUtilAnios)} y
    \texttt{limite = min(fechaCorte, finVidaUtil)}.
    \item Fila inicial en la fecha de compra: depreciación 0, acumulado 0,
    valor real = precio.
    \item Para cada aniversario \texttt{n = 1, 2, 3...} que sea
    $\le$ \texttt{limite}: fila de año completo con VDA. Si el aniversario
    coincide exactamente con \texttt{limite}, terminar (no hay resto parcial).
    \item Si sobra un período menor a un año, contar los \textbf{meses
    completos} de calendario y agregar la fila parcial con
    \texttt{meses $\times$ VDM}. El conteo ajusta por el día:
    \texttt{meses = (hasta.Year - desde.Year) $\times$ 12 + (hasta.Month - desde.Month)},
    y si \texttt{hasta.Day < desde.Day}, se resta 1.
\end{enumerate}

\textbf{Ejemplo oficial de verificación} (AGENTS.md): activo Tecnología de
\$900, comprado el 22/09/2026, fecha de corte 03/08/2027.

\begin{itemize}
    \item \texttt{VDA = (900 $\times$ 0.9) / 3 = 270}; \texttt{VDM = 22.5}.
    \item Entre 22/09/2026 y 03/08/2027 no cabe ni un año completo (el primer
    aniversario, 22/09/2027, es posterior al corte).
    \item Meses completos entre 22/09/2026 y 03/08/2027 = 10 (el mes 11
    cerraría el 22/08/2027, posterior al corte).
    \item Depreciación parcial = $10 \times 22.5 = 225$.
\end{itemize}

El segundo ejemplo oficial (Edificios \$100000, compra 01/01/2023, corte
01/06/2026) ejercita el caso con años completos: 3 filas de \$4500 (2024,
2025 y 2026) más la fila parcial de $5 \times 375 = 1875$, totalizando 5
filas.

La implementación real en \texttt{AssetsService.Domain/Services/DepreciacionService.cs}
sigue exactamente este algoritmo:

\begin{lstlisting}[style=csharp, caption={AssetsService.Domain/Services/DepreciacionService.cs (fragmento)}]
// VDA = VD / VIDA_UTIL_ANIOS (depreciacion por anio completo)
// VDM = VDA / 12 (depreciacion por mes, SOLO para la fila parcial final)
decimal vda = valorDepreciable / categoria.VidaUtilAnios;
decimal vdm = vda / 12;

// 1. finVidaUtil = fechaCompra.AddYears(vidaUtilAnios)
DateTime finVidaUtil = activo.FechaCompra.AddYears(categoria.VidaUtilAnios);

// 2. limite = min(fechaCorte, finVidaUtil)
DateTime limite = activo.FechaCorte < finVidaUtil ? activo.FechaCorte : finVidaUtil;

// 4. Para cada aniversario n = 1, 2, 3... que sea <= limite:
//    fila de anio completo con VDA. Si el aniversario coincide exactamente
//    con limite, terminar (no hay resto parcial).
DateTime ultimoAniversario = activo.FechaCompra;
for (int n = 1; ; n++)
{
    DateTime aniversario = activo.FechaCompra.AddYears(n);
    if (aniversario > limite) break;

    acumulado += vda;
    filas.Add(new FilaDepreciacion
    {
        Fecha = aniversario,
        ValorDepreciacion = vda,
        ValorDepreciacionAcumulado = acumulado,
        ValorReal = activo.PrecioCompra - acumulado
    });
    ultimoAniversario = aniversario;

    if (aniversario == limite) return filas;
}

// 5. Resto parcial: contar MESES COMPLETOS de calendario y agregar
//    la fila parcial con meses * VDM.
int meses = ContarMesesCompletos(ultimoAniversario, limite);
if (meses > 0)
{
    decimal depreciacionParcial = meses * vdm;
    acumulado += depreciacionParcial;
    filas.Add(new FilaDepreciacion
    {
        Fecha = limite,
        ValorDepreciacion = depreciacionParcial,
        ValorDepreciacionAcumulado = acumulado,
        ValorReal = activo.PrecioCompra - acumulado
    });
}
\end{lstlisting}

El conteo de meses completos se implementa con la fórmula exacta de
AGENTS.md, ajustando por el día:

\begin{lstlisting}[style=csharp, caption={DepreciacionService.cs — conteo de meses completos}]
private static int ContarMesesCompletos(DateTime desde, DateTime hasta)
{
    int meses = (hasta.Year - desde.Year) * 12 + (hasta.Month - desde.Month);
    if (hasta.Day < desde.Day) meses--;
    return meses;
}
\end{lstlisting}

\textbf{Por qué aplica}: la corrección se hizo primero dentro del servicio
original y se validó con los dos ejemplos oficiales en
\texttt{DepreciacionApp.Tests} antes de migrar a Onion; los tests
\texttt{Tecnologia\_900\_Compra\_22\_09\_2026\_Corte\_03\_08\_2027\_Genera\_Fila\_Inicial\_Y\_Parcial}
y \texttt{Edificios\_100000\_Compra\_01\_01\_2023\_Corte\_01\_06\_2026\_Genera\_3\_Anios\_Y\_Parcial}
verifican exactamente las tablas descritas arriba.

\section{Pruebas}

La estrategia de pruebas se centra en la regla de negocio más crítica del
sistema: la fórmula de depreciación. Por eso los tests son unitarios sobre
\texttt{DepreciacionService} (la lógica pura del Domain, sin HTTP ni base de
datos), usando xUnit en el proyecto \texttt{DepreciacionApp.Tests}. Se
ejecutan con \texttt{dotnet test} sobre toda la solución.

Los cuatro casos cubren los dos ejemplos oficiales de AGENTS.md y los dos
límites del algoritmo:

\begin{enumerate}
    \item \texttt{Tecnologia\_900\_Compra\_22\_09\_2026\_Corte\_03\_08\_2027\_Genera\_Fila\_Inicial\_Y\_Parcial}:
    ejemplo oficial 1. No cabe ningún año completo; valida el conteo de meses
    completos (10 meses $\times$ 22.5 = 225) y la fila inicial.
    \item \texttt{Edificios\_100000\_Compra\_01\_01\_2023\_Corte\_01\_06\_2026\_Genera\_3\_Anios\_Y\_Parcial}:
    ejemplo oficial 2. Valida el bucle de aniversarios (3 años completos de
    4500) y el resto parcial (5 meses $\times$ 375 = 1875), con el acumulado y
    el valor real de cada fila.
    \item \texttt{Corte\_En\_Aniversario\_Exacto\_No\_Genera\_Fila\_Parcial}:
    caso borde. Si la fecha de corte coincide con un aniversario, el algoritmo
    debe terminar sin fila parcial (1 año completo de 270, valor real 630).
    \item \texttt{Corte\_Despues\_De\_Fin\_De\_VidaUtil\_Se\_Detiene\_En\_FinVidaUtil}:
    caso borde. Si el corte supera el fin de vida útil, la tabla se detiene en
    \texttt{finVidaUtil} con el valor real en el 10\% del precio (90 de 900).
\end{enumerate}

Un fragmento del primer test muestra el patrón: se construye el activo, se
llama a \texttt{CalcularTabla} y se verifican las cuatro columnas de cada
fila:

\begin{lstlisting}[style=csharp, caption={DepreciacionApp.Tests/DepreciacionServiceTests.cs (fragmento)}]
[Fact]
public void Tecnologia_900_Compra_22_09_2026_Corte_03_08_2027_Genera_Fila_Inicial_Y_Parcial()
{
    var activo = new Activo
    {
        PrecioCompra = 900m,
        FechaCompra = new DateTime(2026, 9, 22),
        FechaCorte = new DateTime(2027, 8, 3)
    };

    var filas = new DepreciacionService().CalcularTabla(activo, Tecnologia);

    Assert.Equal(2, filas.Count);
    Assert.Equal(new DateTime(2026, 9, 22), filas[0].Fecha);
    Assert.Equal(0m, filas[0].ValorDepreciacion);
    Assert.Equal(900m, filas[0].ValorReal);
    Assert.Equal(225m, filas[1].ValorDepreciacion);
    Assert.Equal(675m, filas[1].ValorReal);
}

\textbf{Por qué estos casos}: los dos primeros son los ejemplos de
verificación oficiales de AGENTS.md (el criterio de aceptación del proyecto);
los dos últimos ejercitan las condiciones límite del algoritmo (aniversario
exacto y fin de vida útil), que son donde una implementación ingenua suele
fallar. Los tests viejos de la tabla mensual se eliminaron porque ya no
reflejan la regla corregida. Resultado actual: \textbf{4/4 tests pasan}.
